# 财务改造实施与验收记录

本次在现有 React / Flask 系统内实现人民币业务账簿和总账。代码位于当前工作区，尚未部署到生产，也未导入真实期初或业务账册。原订单创建、装箱、报价、原收款、出库和订单历史入口继续保留。

## 已实现的业务链

1. 在财务工作台选择“会计与月结”，设置公司、建账日和收入确认方式，开放会计期间。
2. 录入并核对资金、资产、负债和权益的期初凭证，以及客户/供应商期初账单、期初预收预付。期初预收不再增加银行余额。
3. 需要接入旧订单时，先预览当天净余额、未决收款和差价等来源。确认金额、到期日、来源摘要与原因后接入。当前快照只支持当天建账；历史日期需要人工核准资料，不能反推历史货重。
4. 客户/供应商账单保存草稿、核对明细、确认生效；自动生成借贷平衡的凭证。关联订单只保存来源，不改变订单状态。
5. 登记真实收付款，确认生效后可分次核销、跨多张同客户账单分配，也可保留预收预付。退款受可用余额限制，核销与退款不能重复占用资金。
6. 错单使用贷项、冲销或撤销核销；原单、原分配、修改前后值、操作人及依据保留。按需用履约模块分次确认收入。
7. 导入银行流水，预览去重后保存；匹配同账户、同金额及同方向的真实收付款。银行对账本身不发起转账。
8. 查询或打印往来对账单，导出试算表，核对账龄、科目明细和资金流。期初未确认时标识待核对口径。
9. 旧来源后续变化进入首页待核对队列。新账单变化与资金变化分别匹配新账簿依据；不能只凭总净额相同点击完成。已关联凭据失效会再次出现待办。
10. 关账前检查期初、草稿、银行匹配、借贷平衡、更早期间、旧账接入差异等。重开仅管理员，记录原因。错误接入在期初未确认且无后续使用时可以撤销重来。

## 设计与兼容性

- 工作台采用统一的浅色卡片、深色标题、清晰金额层级、固定状态语义、适配窄屏的表单和可横向滚动表格。
- 草稿和生效、结清和核销、资金和收入分别呈现。失败态不伪装为零余额；列表与审核队列使用服务端分页。
- 原应收参考页默认包含往期欠款，允许按日期筛选，并说明其报价口径；正式账簿使用冻结明细及凭证。
- 每张新账单和资金单有可读历史。旧收款已接入同事务审计，无法还原的旧变更会显示历史范围提示。
- 同事务事件共享关联号；审计写入失败回滚业务。生效操作防重复、草稿防覆盖，已生效金额通过关联更正。

## 部署前实际操作

1. 审核当前两个子仓库的变更。工作区同时存在其他任务的 OAuth/MCP 改动；当前 Alembic 链为 `e05 → f16(财务子账) → 027(会计) → g27/h38(OAuth/MCP) → 138(旧账接入)`，发布需审核完整链，不可遗漏父版本。
2. 在备份恢复出的测试环境安装后端依赖，执行 `alembic upgrade head`，再构建前端。先比较迁移前后的原订单数量、原收款金额和关系记录。
3. 只在明确标记为测试库的独立 MySQL 环境执行并发测试，环境变量与保护条件见 `tests/finance/test_ledger_concurrency.py`。不要指向生产库。
4. 使用经过财务核准的真实账册核对建账日、期初、收入政策、科目及税率。部署不会自动推断这些信息或搬入真实余额。
5. 选取真实但已核对的完整业务样本，走账单、部分收款、贷项退款、供应商付款、对账和关账；确认总账、子账和资金来源一致后再扩大使用。

接口和具体字段见 [API v1.20 财务](API-v1.20-finance.md) 与 [实现契约](finance-v2-contract.md)。

## 当前明确边界

新账簿先支持 CNY。供应商账单按服务成本记账，其他经营费用、资产、工资和折旧可通过明确科目的记账凭证录入；尚未实现专门的资产折旧计划、薪税计算或自动费用分摊。银行匹配为一笔流水对一笔收付款，不包含银行直连和自动实际付款。资金流视图按凭证类别归集，不能宣称已完成公司适用准则下的全部法定财务报表或税务申报。真实资料与政策核准、生产迁移及视觉验收仍是正式上线前的工作。
