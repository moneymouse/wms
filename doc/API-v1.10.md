# API v1.10：纸单自动识别、操作人员与唛头命名

日期：2026-10-02。基于 [API v1.9](API-v1.9.md) 的回传流程，保留既有角色权限、候选隔离和人工确认机制。

## 上传后自动识别

`POST /api/intakes` 仍使用 multipart，工人只需提交 `photos`；不增加必填资料或识别按钮。照片和后台识别任务标记在同一事务中保存，提交成功后启动识别线程，HTTP 201 返回回传记录，通常 `recognition_status=running`。

照片上传成功后即使识别服务未配置、调用失败或线程启动失败，照片仍保留、业务状态仍为 `pending`。上传人可以离开页面，文员在后台查看状态并重试。识别不直接生成正式装箱单，也不覆盖人工草稿。

限制为 1 至 8 张，JPEG、PNG、WebP，单张不超过 10MB、图片合计不超过 24MB。请求体上限 25MB，预留 multipart 元数据空间。超限不会保存回传。旧记录不批量补跑；文员可以沿用 `POST /api/intakes/:uid/recognize`，携带最新 `version` 重试。

## 新增记录和照片字段

| 字段 | 含义 |
| --- | --- |
| `display_name` | 纸单名称，按人工已保存的唛头、识别唛头、上传提示、`纸单-UID前8位` 回退；识别完成或文员保存修正后自动更新。 |
| `operator_name` | 纸上的作业人员，审核保存的值优先，否则来自识别候选。与 `submitted_by_name`（登录回传人）分开，不自动绑定系统用户。 |
| `photos[].filename` | 以纸单名称生成的文件名，例如 `ABC-001-01.png`、`ABC-001-02.jpg`，按照片顺序区分页；移除文件名中的路径和控制字符。 |
| `photos[].original_filename` | 上传时的原文件名，保留来源信息。 |

图片仍保存在数据库，不移动或改写原图字节。图片接口 `GET /api/intakes/:uid/photos/:photo_uid` 的 `Content-Disposition` 使用当前生成文件名；前端原图下载也使用此名称。回传 UID 始终不变，相同唛头的多次上传仍是独立记录。

新草稿与候选结构：

```json
{
  "mark": "ABC-001",
  "operator_name": "张三",
  "boxes": [
    {"box_number": 1, "item_name": "衣服", "count": 12, "weight": 8.5},
    {"box_number": 2, "item_name": "衣服", "count": 10, "weight": 7.2}
  ]
}
```

操作人员可空、最多 128 字。旧草稿没有该字段时仍兼容；保存时归一化为空字符串。操作人员保存在回传 JSON 中，不需要新增数据库列或修改旧迁移。确认后可从原回传追溯人员。

## 按唛头查询

`GET /api/intakes?mark=ABC-001&status=pending&page=1&page_size=20` 新增可选 `mark`，对人工草稿唛头、识别候选唛头和上传提示作不区分大小写的包含查询，最长 64 字。`%`、`_` 按普通字符处理。查询仍在角色权限约束内分页，操作工只能查询本人记录。

页面列表按唛头显示纸单名称，识别中的列表自动刷新；文员能在采用识别候选前找到对应原图。读取列表或详情时，超过 5 分钟的识别标为失败，允许核对人员重试。

## 识别规则

- 从“操作人员、装箱人、作业人员、签名”等纸面区域抄录姓名，无法辨认留空；多人或不一致时警告，不推断登录上传人或核对人为操作人。
- 同一唛头连续相邻的箱号，品名空白或明确标注“同上、〃”时，可以沿用上一个明确品名；遇到新商品切换。
- 解析后处理仅在唛头明确、相邻正整数箱号及真实逐箱数字证据成立时继承品名，并附警告供文员复核。缺号、断号、模糊品名或不明确批次会中断继承。
- 件数、重量、箱号不继承或猜测；表头、空行和合计行不生成箱子。多唛头仍要求拆分。

## A4 模板

正式空白模板位于后端 `static/templates/paper-packing-list-a4.pdf`，一页 A4、18 行；包含唛头、作业日期、操作人员、页码、逐箱箱号/品名/件数/公斤重量/备注、合计和核对人。连续品名建议写“同上”或“〃”，跨页首行重新填写完整品名。

可用 `scripts/generate_paper_intake_template.py --output PATH --font PATH` 重新生成（需要 ReportLab 和中文 TTF/TTC 字体）。正式创建页通过鉴权 `GET /api/intakes/template` 下载已生成的文件，实际用户上传会自动识别。正式集成说明见 [API v1.12](API-v1.12.md)。

后台仍使用 MVP 的进程内线程；服务重启后需由核对人员重试超时任务。真实手写识别质量需通过实际填写纸单验证。

## 本次验证

后端流程 29 项、识别适配 65 项、前端交互 21 项定向测试通过；前端构建通过，仍有其他既有页面的 lint 提示。

通过本地隔离预览上传一张合成印刷纸单，并实际调用配置中的识别服务：仅提交照片即自动进入识别，识别出 `VERIFY-1002` 和纸单操作人“测试工人”；连续第 2 箱空白品名、第 3 箱“同上”均沿用“鞋”，第 4 箱新商品切换为“衣服”，分别保留逐箱件数和重量。文员按唛头查询成功，照片自动命名为 `VERIFY-1002-01.png`。采用候选、保存草稿并刷新后，人员与四箱记录均恢复。该验证不代表真实手写样本准确率已验证。
