# API v1.14：资料更新与出库登记

日期：2026-10-02。本版把出库确认、登记时间和箱成本冻结集中到 `services/outbound_service.py`。现有录号和批量上传入口仍一次完成原有操作；也支持只更新资料以及先出库、次日再补号码。前端本轮无需新增操作步骤。

`transfer_id` 是原单号，`waybill_id` 是二级代理提供的转单号。号码本身是资料，不代表实物发生出库。工人纸上记录、业务员次日补录的现有流程可以继续使用默认兼容行为。

## 更新资料：默认兼容补登记

现有接口：

- `PUT /api/cargo/<uid>`：普通包裹或装箱单箱子。
- `PUT /api/box/<uid>`：装箱单箱子。

默认 `confirm_outbound: true`。只有请求提交了非空 `waybill_id` 时，应用服务才在同一事务内组合「更新资料」和「对尚未出库货物登记出库」。号码与已有值相同也能为待出库货物补登记。只更新备注、重量等字段不会顺带出库。

```json
{"waybill_id":"WB-123"}
```

仅更新资料可明确传 `confirm_outbound: false`：

```json
{"waybill_id":"WB-123","confirm_outbound":false}
```

JSON 布尔值和字符串 `"true"` / `"false"` 均可识别，其它参数值返回 400。成功响应保持 `{"code":200,"msg":"success"}`。禁止客户端直接写出库 `status` 或 `date`；货物入口仍拒绝这类字段。

已出库或进入后续追踪状态的货物更正号码不会再次出库，不重写原 `date`，不重建成本，不补造新的出库事实。无变化的重复请求不会产生订单版本。订单已锁定时，更正原单号或转单号仍需管理员开启修订；原有收据历史对重量、客户和成员关系的保护继续生效。修订中允许首次登记出库，奖金等其它下游动作仍受各自原有守卫约束。

货物入口的原有资料编辑权限沿用；装箱单箱子资料编辑和兼容出库组合要求角色为 `admin`、`store_manager`、`salesperson` 或 `clerk`。普通包裹请求兼容出库组合时也必须具有上述出库角色。服务在确认动作边界再次校验请求或显式传入的操作人角色。

## 批量上传

`POST /api/order/upload/transfer_table`，继续使用 multipart 文件上传字段 `file` 和 `filename`。

默认表单参数 `confirm_outbound=true`，匹配原单号的货物统一更新转单号并为未出库货物补登记。表单明确传 `confirm_outbound=false` 时只更新号码；追踪注册仍在数据库提交后执行。

批量上传已由 [API v1.38](API-v1.38-partial-waybill-upload.md) 改为按订单分别提交。某个订单导入失败时，仅回滚该订单的号码、出库状态和时间、箱成本、出库事实和订单版本，继续保存其他订单。同一订单的多个导入箱子仍在同一事务内处理。重复相同号码的已出库记录不再次生成成本、历史或版本，但响应中仍计为保存成功。没有匹配货物的原单号不创建货物，作为失败项报告；同一原单号匹配多个货物时仍分别处理全部匹配记录。

客户归属校验比较装箱单的 `customer_id` 与订单关联的客户 ID。归属不一致时，批量上传的 `failed_list[].reason` 包含实际失败箱子的原单号、装箱单唛头、箱号、订单号以及双方客户 ID。部分成功返回 HTTP 200、`code=207`；全部失败返回 HTTP 400、`code=400`。手动填写及独立确认出库遇到同类错误时仍返回 HTTP 400，定位信息放在 `msg` 中。

默认出库组合要求上述四种出库角色；纯更新模式沿用现有资料修改权限，涉及装箱单箱子时仍需箱资料编辑角色。响应保留原字段并新增成功明细、失败明细及独立追踪错误，详见 v1.38。17Track 失败发生于提交之后，数据已保存，不会回滚；调用方应处理追踪失败，不能当作数据库未写入而撤销用户资料。

## 独立确认出库

新增 `PUT /api/cargo/<uid>/outbound`，普通包裹和装箱单箱子共用。JWT 请求头 `x-token`，允许角色为 `admin`、`store_manager`、`salesperson`、`clerk`。无需 `waybill_id`；取得转单号之前即可登记实物已搬走。

请求体为 JSON 对象，可以为空对象；无请求体也等同空对象。唯一可选字段是已知的实际发生时间 `occurred_at`：

```json
{"occurred_at":"2026-10-01T16:30:00+08:00"}
```

该字段必须为 ISO 日期时间字符串，不能只给日期。不知道实际时间时传 `{}` 或 `{"occurred_at":null}`，保存为未知，不推断为昨天或当天。非法 JSON、数组、标量或其它字段返回 400，并且不出库。

首次确认响应示例：

```json
{"code":200,"data":{"confirmed":["cargo-uid"],"unchanged":[]}}
```

已出库重试返回 `confirmed: []` 和 `unchanged: [uid]`，不更新时间、成本或事实。重试仍需有效出库角色；并发发生状态竞争时可返回 409，请刷新后重试。

旧 `POST /api/cargo/<uid>/output` 和 `POST /api/packing-list/<uid>/ship` 继续返回 410；本版没有恢复旧入口。旧 `BoxModel.batch_ship` 保持停用，已清除无调用方的 `_legacy_batch_ship` 第二套出库实现。

## 共同校验、事务与成本

首次确认要求货物未归档、有有效且未归档的归属订单、重量为有限数字且大于 0。装箱单箱子另要求装箱单有效且未归档；双方均明确客户时要求客户归属一致。历史或新建资料未指定客户时不要求先补做客户迁移。普通包裹没有装箱单校验，也不创建箱成本表记录。

服务按订单、货物、装箱单的顺序锁定；同类记录按 UID 排序锁定。重读后再校验归属和 ID 集合，防止等待锁时归属变化或被删除。MySQL 行锁和条件状态写入共同防止重复确认；SQLite 通过条件状态写入检测并发竞争。号码、状态、登记时间、成本、出库事实、订单版本在同一事务内提交；任何一步失败整体回滚。17Track 单条后台注册或批量注册始终在提交后执行。

装箱单箱子首次确认即冻结当时的运输渠道、重量和现行成本，不要求已取得转单号。原快照中的号码可能为空；次日补号不会修改这个历史快照。`occurred_at` 只记录实际发生时间，本版不按该时间回溯历史渠道成本。已经存在成本快照的待出库箱不能覆盖旧快照，返回 409。撤销出库沿用原有财务保护和成本删除规则，再次确认追加新的出库事实；不改造退货或订单锁整体设计。

## 时间、持久化与迁移

`CargoTable.date` 保持旧含义：首次登记出库的服务器本地时间，格式 `YYYY-MM-DD HH:MM`。它不是已核实的实物发生时间。新 `cargo_outbound_records` 表保存每次登记事实：

| 字段 | 含义 |
| --- | --- |
| `cargo_uid` / `order_uid` | 当时的货物与订单标识 |
| `occurred_at` | 可空的实际发生日期时间，原样保存显式输入 |
| `recorded_at` | 本次登记时间，与首次写入的 cargo.date 相同 |
| `source` | `explicit`、`cargo_details`、`box_details` 或 `waybill_import` |
| `operator_id` / `operator_name` | 请求中的操作人，内部可信任务未提供时可空 |

记录按次追加；同次重复确认没有新记录。已有历史出库货物改号或重试不回填假记录。历史标识不新增外键约束，货物或订单按原规则归档/硬删除时仍保留登记记录，不因此引入删除失败。箱成本等既有不可变快照对硬删除的限制继续生效。

提供 Alembic 版本 `20261002_e05b6c7d8e9f_cargo_outbound_records.py`，依赖 `df4a5b6c7d8e`。上线前需按现有 Alembic 流程应用该迁移；本轮仅编写迁移，没有对真实业务数据库执行。无历史时间回填，没有改变已有 `date`。

## 内部调用与错误

`CargoModel.update`、`BoxModel.update` 和 `CargoModel.create` 默认只保存资料；创建时携带号码也不会隐式出库。模型通用更新禁止直接改货物出库状态/时间。应用层可独立调用 `update_cargo_details(..., confirm_outbound=False)`，或明确组合 `confirm_outbound=True`。`confirm_outbound([uid, ...], occurred_at=..., operator=...)` 支持独立原子批次，无需号码。`confirm_in_session` 只供已按统一顺序锁行且由调用方管理版本和事务的内部组合使用，不应独立提交。

模型可接收服务会话，仅 flush；顶层服务统一版本和 commit/rollback。内部无请求上下文且没有显式操作人的调用仅供可信程序任务使用；HTTP 入口必须执行认证和角色授权。批量兼容包装 `apply_waybill_table` 委托统一服务，提交后注册追踪。

常见状态：400 表示非法请求或首次出库资料不齐，403 表示动作权限不足，404 表示货物不存在，409 表示订单编辑/财务保护或并发冲突。新独立确认响应中的 `unchanged` 表示已经出库，不表示已重写登记记录。

隔离测试命令：`python -m pytest --confcutdir=tests/outbound -q tests/outbound`。测试使用独立 SQLite、单独注册 Blueprint，并模拟外部追踪；不导入真实 app 的备份或管理员初始化流程。
