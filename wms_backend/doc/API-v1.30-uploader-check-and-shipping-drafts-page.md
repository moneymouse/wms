# API v1.30：上传者检查纸质单与出货确认单草稿页面

## 纸质装箱单上传

纸质单上传按“选择照片 → 识别与检查 → 完成上传”执行。上传者对照原图检查唛头、箱号、品名、件数、重量及实际操作工人，修正后明确勾选已检查，才可完成上传。识别失败时仍可对照原图手动填写和检查。

`POST /api/intakes` 仅暂存照片并启动识别，不表示上传完成，也不创建正式装箱单。照片及检查草稿继续持久化，重新打开后可以接着处理。

- `GET /api/intakes/<uid>`：读取本人未完成上传；已完成的来源记录继续按既有正式单可见范围供工作人员读取。
- `PUT /api/intakes/<uid>/draft`：上传者保存本人检查内容，仍使用 `{version,draft}`。
- `POST /api/intakes/<uid>/recognize`：上传者重试本人识别任务，使用 `{version}`。
- `POST /api/intakes/<uid>/confirm`：请求 `{version,reviewed:true}`。必须由上传者操作，识别仍在进行时不能完成；完整字段和批准工人校验通过后，一次事务生成状态为 `completed` 的装箱单、箱子及工人绑定。`confirmed_by` 为上传者本人，重复完成不会创建第二份单。
- `GET /api/intakes/workers`：全部上传角色可查询批准的实际操作工人。

上传角色为管理员、店长、业务员、文员、工人及兼容员工；角色不赋予代他人检查或完成未上传记录的权限。已确认的来源记录不可通过检查草稿接口修改。

`GET /api/intakes/my-packing-lists` 继续限定当前用户本人，未完成照片上传状态改为 `uploading`，带来源 UID，前端显示“未完成上传”和继续检查入口。可选 `status=uploading|draft|completed` 在分页前筛选，供创建页恢复未完成上传。纸质来源的已完成装箱单显示“已核对”。

原待核对纸质单列表页面及 `/intakes`、`/intakes/:uid` 前端路由已移除。`GET /api/intakes` 不指定来源装箱单时返回 410；仅保留 `?packing_list_uid=<uid>` 查询已完成纸质单来源及私有原图。既有未完成记录保留为上传者的未完成上传，不自动确认、不转交其他人。

前端继续上传页面为 `/packing-list/upload/:uid`。完成上传前提供识别结果、照片预览、人员选择、疑点、字段验证及未保存内容离开保护。只有确认返回已生成装箱单后才显示上传完成。

## 出货确认单草稿

装箱单列表标题右侧入口替换为“出货确认单草稿”，原“出货确认单（PDF）”按钮也打开草稿页面。页面路由：

- `/shipping-confirmation-drafts`：草稿列表和新建编辑区域。
- `/shipping-confirmation-drafts/<uid>`：直接打开已有草稿，便于刷新和继续编辑。

编辑改为完整页面，保留跨装箱单选箱、跨页选择、逐箱或批量填写代理及备注、保存、重新打开、移除、删除与 PDF 打印。离开页面前保护未保存内容，版本冲突保留当前输入并支持另存副本。权限与服务器草稿接口沿用 [API v1.27](API-v1.27-packing-shipping-drafts.md)。

本次不新增数据库字段或迁移；沿用纸质单暂存表和出货确认单草稿表。历史已完成装箱单及来源照片保留。
