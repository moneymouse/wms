# API v1.47：物流推送落库与本地包裹详情

订单详情的 `GET /api/orders/<uid>/cargo` 只读取本地包裹及已保存的物流快照，不调用 17TRACK 查询、注册、重新推送或写入数据库。前端刷新也只刷新本地数据；运单新增或变更后的既有后台注册流程继续保留，以便 17TRACK 向已配置的 webhook 地址发送更新。独立的 MCP 主动物流查询接口沿用原行为。

## 包裹响应

既有货物字段保持不变。`status` 始终是仓库业务状态整数，不再在读取响应中临时替换为物流子状态。新增或保留以下独立物流字段：

| 字段 | 含义 |
| --- | --- |
| `track_status` | 当前物流子状态，缺子状态时使用主状态；无快照为 null |
| `desc` | 当前物流状态说明 |
| `events` | 所有承运商轨迹事件的展示集合，完整事件去重；有可解析 UTC 时间的事件按降序排列，其余保持稳定顺序 |
| `track_info` | 推送包含的完整物流详情；无快照为 null |
| `tracking_received_at` | 本地接收此次当前快照的 UTC 时间，ISO 8601；不是物流事件发生时间 |
| `tracking_pending` | 尚无匹配当前包裹、订单和转单号的可展示快照 |

前端普通包裹使用独立 `track_status` 显示物流状态。装箱单未出库时继续显示“待出库”；已出库才显示物流状态。存在转单号但没有快照时显示“等待物流推送”，不将缺少推送当成 17TRACK 查询失败。仓库状态仍决定重量编辑、移除和出库等既有权限。

## 推送持久化

`POST /api/webhooks/17track` 沿用 API v1.46 的原始正文验签与严格业务关联检查。所有 `TRACKING_UPDATED` 状态均保存完整记录，而不仅是异常；正常状态不会自动解决人工异常。

新增 `parcel_tracking_updates` 表保存包裹、订单、转单号快照、规范 JSON 内容、稳定事件键、接收时间、来源时间水位、当前快照标记及关联异常 UID。正文使用 MySQL LONGTEXT，支持接口 2 MiB 请求上限内的完整长轨迹。历史不依赖业务实体外键，因此删除包裹或订单不会顺带删除历史事实；本次不新增人工历史查询接口。

同一完整内容重发只保留一次记录、不重复更新当前快照或发送消息。缓存变更、接收历史、异常登记、异常历史和消息通知在同一事务内提交；任何失败全部回滚，返回非 200 供 17TRACK 重试。同包裹、同转单号的原事件在移单后重发仍被确认，但不会将旧订单快照应用到新订单。包裹列表排除在读取过程中已移出当前订单或已归档的包裹，展示缓存也必须匹配当前订单与转单号。

响应 `data` 含 `processed`（匹配的更新数，含重发）、`recorded`（新增接收历史数）、`updated`（成为当前快照数）、`ignored`（未知/过期关联或其他事件数）、`stale`（新记录中未成为当前快照数，含内容不完整）以及 `exception_uids`。

只有成为当前快照的 `Exception` 状态才登记异常并通知业务员。旧回调只记录，不覆盖较新物流、不新建异常，也不会重新打开已解决的异常。`TRACKING_STOPPED` 沿用确认接收的行为，保留已有物流详情，不主动重新追踪。

## 时间与乱序限制

[17TRACK v2.2 官方文档](https://asset.17track.net/api/document/v2.2_en/index.html)说明通知含完整物流信息，但未提供全局递增版本号或顺序保证。系统以可解析且带时区的 `providers[].latest_sync_time` 最大值作为来源时间水位；缺少同步时间时使用 `latest_event.time_utc/time_iso`。所有可比较时间统一为 UTC，不依据无时区的 `time_raw` 排序。

对同一物理包裹和转单号，明显更旧的水位仅留历史，水位在移单后仍有效。已知当前水位而新回调缺少有效时间时，也只留历史；相同水位但内容不同允许更新。双方均无有效时间时采用接收顺序，这不能证明物流内容的真实先后。多承运商最大同步时间也是工程防旧策略，不能提供官方不存在的全局顺序保证。
