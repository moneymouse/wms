# Finance v2 implementation contract

## Unified customer receipt/payment update

New customer money records use `FinancePayment` exclusively. Sales staff can create/read/edit/cancel only their own non-opening customer payments (incoming receipts or outgoing refunds). Finance/admin can read all. `POST /payments/:id/submit` changes draft to pending; `POST /payments/:id/post` confirms funds for finance/admin, and a pending record's creator cannot approve it. Existing finance-authored draft posting remains supported. `POST /payments/:id/return` requires `{version,reason,idempotency_key}` and returns pending to editable draft on the same ID. Posting and allocations remain finance/admin-only. All edits/actions continue to require version; command retries support idempotency keys.

Create/edit accepts optional `reference_order_uids:[]`. These are **description only**, not allocations. Every referenced order must belong to the selected customer, but it may have no cargo, quotation or amount and may belong to another salesperson. Returned `reference_orders:[{order_uid,order_number,customer_id}]` is a saved snapshot. Payment amount is never recalculated from weight, quotation or order changes. Reference orders cannot confer access to other customers or change allocation balances.

Payment responses add `submitted_at`, `submitted_by_id/name`, `reviewed_at`, `reviewed_by_id/name`, `review_remark`, `reference_order_uids` and `reference_orders`. Pending and draft amounts do not affect funds/accounting/unallocated posted balances. Returned drafts expose the finance reason and can be corrected and resubmitted.

Business lookup routes (salesperson/finance/admin): `GET /payment-options/customers?q=&p=&s=`, `/payment-options/accounts?q=&p=&s=`, and `/payment-options/orders?customer_id=&q=&p=&s=`. All return `{items,total,page,page_size}` in data. Customer rows are `{id,name}`; active CNY account rows expose `id,name,account_type,account_number,currency`, never account balances to salespeople. Order rows include empty/unquoted orders within the selected customer, ordered by `create_date DESC, uid DESC` before server pagination. They retain `order_uid,order_number,customer_id,customer_name` and add order-list aliases `uid,order_id` plus `transportation,receiver,receiver_phone,mail,country,province,city,address,en_name,cn_name,post_code,zip_code,tag_all,create_date,update_date,total_weight,cargo_count`. `order_date` displays creation time with original order date as a legacy fallback; missing order numbers use UID. Search `q` matches these operational text fields. Customer phone/WeChat, quotations, costs and financial balances are excluded. Financial account editing and vendor access remain finance-only.

`GET /payments/:id/pdf` returns `{code:200,data:base64,filename,mime_type:'application/pdf'}` with the same per-payment ownership check as detail/history. It prints actual payment amount, selected funds account, status and approval, and labels reference orders as notes that do not represent settlement. Draft/pending PDFs explicitly do not prove finance-confirmed receipt. Payment list supports `created_by_id` for finance/admin; sales scope cannot be broadened by filters.

Legacy `PaymentReceipt` records stay historical and are not copied to posted `FinancePayment`: copying would double count cash already included in opening funds and net cutover balances. Legacy new receipt creation is retired at the controller/UI boundary; existing pending legacy receipts retain their old approval/rejection path until cleared, then reviewed net balances can be connected through the existing cutover workflow. Historical PDF and audit reads remain available.

All routes use `/api/finance/v2` and JWT. Accounting/document/allocation routes require `finance` / `admin`; the unified customer payment routes described above also permit scoped salesperson access. JSON success is `{code:200,data:...}`; errors use actual HTTP 400/403/404/409. Money is a fixed two-decimal string; quantity and unit price strings have four decimals. CNY only for this release. Lists return `{items,total,page,page_size}` inside `data`, with `p`, `s`, `q` filters. Mutation dates are ISO `YYYY-MM-DD`; timestamps are ISO local time. Every update/action requires `version` and conflicts return 409. POST create/action accepts `idempotency_key` (body or `Idempotency-Key` header); replay with changed body returns 409.

## Documents

`GET/POST /documents`, `GET/PATCH /documents/:id`, `POST /documents/:id/post`, `POST /documents/:id/cancel`, `POST /documents/:id/reverse`.

Document fields: `id`, `number`, `document_type` (`customer_invoice`, `vendor_bill`, `customer_credit`, `vendor_credit`), `partner_type` (`customer` / `vendor`), `partner_id`, `partner_name`, `document_date`, `due_date`, `currency`, `reference`, `memo`, `status` (`draft`, `posted`, `cancelled`), `version`, `total_amount`, `allocated_amount`, `residual_amount`, `payment_status` (`unpaid`, `partial`, `paid`), `original_document_id` (required for credit), `reversed_by_id`, `created_at`, `posted_at`, `created_by_name`, `lines`.

Create accepts `document_type`, `partner_id`, `document_date`, optional `due_date/reference/memo/original_document_id`, `lines:[{description,quantity,unit_price,tax_rate,order_uid?}]`. Quantity > 0, price >= 0, tax_rate 0..100; each line returns `subtotal`, `tax_amount`, `total_amount`, `order_number` snapshot. Defaults quantity 1, tax_rate 0. Order link is read-only and does not post/update the legacy order or its receivable. Editing is draft-only and uses the same payload plus `version`. Posting freezes all fields. Cancellation is draft-only and needs `reason`. Reverse accepts `version,document_date,reason`; it creates and posts an exact credit for a posted invoice/bill without an existing posted credit, links it and reconciles the unpaid part. Use a separately created credit for partial reductions. Credit posting is capped by original amount minus already posted credits. Existing payments remain factual.

Filters: `document_type`, `status`, `partner_id`, `payment_status`, `date_from`, `date_to`, `q`.

## Payments and reconciliation

`GET/POST /payments`, `GET/PATCH /payments/:id`, `POST /payments/:id/submit`, `POST /payments/:id/return`, `POST /payments/:id/post`, `POST /payments/:id/cancel`, `POST /payments/:id/reverse`.

Fields: `id,number,direction` (`incoming/outgoing`), `partner_type`, `partner_id`, `partner_name`, `account_id`, `account_name`, `payment_date`, `amount`, `currency`, `reference`, `memo`, `status` (`draft/pending/posted/cancelled/reversed`), `version`, `allocated_amount`, `unallocated_amount`, `created_at`, `posted_at`, `requires_submission`, descriptive order snapshots and approval fields described above. Create requires direction, partner, account, payment_date, amount > 0. Sales-created records have `requires_submission=true` and cannot be posted directly from draft. Post confirms actual funds; reverse needs `version,reason,payment_date` and all allocations first reversed. Draft cancellation needs reason. Unallocated posted amounts are customer advances/vendor prepayments (or refund balances for opposite direction).

`GET /allocations?payment_id=&document_id=&credit_document_id=`; `POST /allocations` takes `{payment_id OR credit_document_id,version,allocations:[{document_id,amount}],reason?}`; `POST /allocations/:id/reverse` takes `{version,reason}`. Allocation fields: `id,payment_id,credit_document_id,document_id,document_number,amount,status` (`active/reversed`), `version,created_at,reversed_at,reason`.

Incoming customer payment matches customer invoices; outgoing vendor payment matches vendor bills. Customer refunds (outgoing) match customer credits; vendor refunds (incoming) match vendor credits. Credit notes can offset an invoice/bill of the same partner. All sources and targets must be posted, same partner/currency, with sufficient residual. Multiple/partial allocations are atomic and cannot overuse funds. Reversal retains the allocation and releases both balances. No cross-partner offset.

## Master data and overview

`GET /partners?partner_type=customer|vendor&q=` returns `{items:[{id,name,partner_type}],total}`. Customers reuse existing customer IDs.

`GET/POST /vendors`, `PATCH /vendors/:id`: `id,name,contact,phone,memo,active,version`.

`GET/POST /accounts`, `PATCH /accounts/:id`: `id,name,account_type` (`bank/cash/other`), `account_number,currency,active,version,balance`. No arbitrary opening balance in the funds module; opening accounting entries are handled by accounting. Referenced account identity/currency is immutable after posted usage; label/memo may change with audit.

`GET /dashboard?as_of=YYYY-MM-DD` returns `{as_of,receivable,payable,customer_credit,vendor_credit,customer_advances,vendor_prepayments,posted_receipts,posted_payments,account_balance,draft_documents,draft_payments,overdue_receivable,overdue_payable,recent_documents,recent_payments}`. Amounts are strings. It includes only the new independent ledger, not old receipts or quotation estimates.

`GET /aging?partner_type=customer|vendor&as_of=YYYY-MM-DD` returns `{as_of,partner_type,totals:{current,days_1_30,days_31_60,days_61_90,days_over_90,total},items:[{partner_id,partner_name,current,days_1_30,days_31_60,days_61_90,days_over_90,total,documents:...}]}`. Uses posted document date / effective allocation and reversal dates at cutoff; historical balances do not drift with cargo edits.

## Backend integration contract

Models in `data.finance.ledger`: `FinanceVendor`, `FinanceAccount`, `FinanceDocument`, `FinanceDocumentLine`, `FinancePayment`, `FinanceAllocation`, `FinanceIdempotency`. Tables use `finance_` prefix. Services pass the same session into audit and accounting. Ledger mutation transaction never commits inside an accounting hook.

Accounting hooks in `services.finance_accounting_service`:

* `post_document(session, document, actor)` called after document fields/state are set and flushed; document has `.lines` relationship; total/subtotal/tax are Decimal. Credits reference `.original_document_id`.
* `post_payment(session, payment, actor)` after posted state; payment has direction/partner/account/date/amount.
* `reverse_payment(session, payment, actor, reversal_date, reason)` while original payment is still posted, then ledger marks reversed and records `.reversal_date`.
* Allocation/unal­location does not change control-account totals and needs no accounting entry.

Audit calls use `record_audit(event_type='finance_document|finance_payment|finance_allocation|finance_vendor|finance_account', target_type=..., target_id=..., action=..., before_data=..., after_data=..., remark=..., session=session, operator_payload=actor)` before commit. Separate history endpoints are provided by the audit workstream.

## Final integration additions

* Documents and payments accept and return `is_opening` (boolean, default false). Only customer invoices/vendor bills and normal incoming-customer/outgoing-vendor advances support it. Dates must equal accounting settings `opening_date`, and opening balances must still be unconfirmed, including at posting time. Opening document due dates may predate the opening date, preserving the true aging. Opening amounts offset opening equity and do not create current revenue/cost or bank movements; bank opening balances are entered exactly once through an opening journal entry.
* Dashboard `account_balance` and account `balance` use posted journal lines, including opening funds, transfers and manual entries. `posted_receipts/posted_payments` use actual payments and exclude opening advances. Customer/vendor advance and credit metrics are net of already posted unallocated refunds for that same partner.
* Opposite-direction payments are refunds. Posting is capped by unallocated normal payments + posted unallocated credits - already posted unallocated refunds. Posting or allocation cannot backdate into a historical shortfall. Refunded advances cannot be reused for invoice allocation. A refund can be allocated to a credit; direct advance/refund pairing is represented by the partner net balance until a separate payment-offset operation is introduced.
* `GET /accounts/:id/history` and `/vendors/:id/history` use the same audited, finance/admin-only response as document/payment history. Existing account identity cannot change after any payment, journal line or bank transaction references it.
* Allocation accepts optional `allocation_date`; reversal accepts optional `reversal_date`, both defaulting to today and requiring an open accounting period. Effective dates cannot precede the involved documents/payments. Credit posting separately caps cumulative gross, net and tax by the original document.
* Document lists support `partner_type`, `open_only=1`, and `overdue=1`. Allocation list rows include `payment_number` and `credit_document_number`. Document reverse returns `{document,credit}`.

## Reviewed legacy cutover

All routes below use `/api/finance/v2/legacy` and finance/admin permissions. The automatic route only handles a current-day balance cutover: `cutoff_date = accounting opening_date = today`, an open period, and unconfirmed opening balances. It never reconstructs historical weight or posts the full old quotation as new revenue. Historical migrations use manually verified opening documents instead.

* `GET /orders?q=&p=&s=` provides an old-order selector.
* `GET /preview?order_uid=&cutoff_date=` returns `{order_uid,order_number,customer_id,customer_name,cutoff_date,snapshot_at,source_hash,source,import_kind,amount,can_import,blockers,existing_link_id,notice,due_date_notice}`. Source includes quotation, cargo, receipt and adjustment snapshots and two-decimal strings for `receivable_amount`, `received_amount`, `settlement_difference`, `signed_balance`. Missing/ambiguous customers, archived facts, pending quotation/receipt/adjustment or incomplete settlement snapshots block import.
* `POST /import` takes `{order_uid,cutoff_date,source_hash,reason,confirmed:true,account_id?,due_date?,idempotency_key}`. The service locks and rereads the source; a stale hash or existing per-order baseline is rejected. Positive balance creates and posts only an opening invoice for the net unpaid amount; negative balance creates only an opening customer advance (account required, no bank movement); zero creates a baseline without a journal. Existing receipts never become available cash again. Due date defaults explicitly to the cutover date because the old system has no reliable due date; reviewers can supply an evidenced earlier due date.
* `GET /links?p=&s=&q=&status=current|drift`, `GET /links/:id`, and `GET /links/:id/history` expose the saved baseline, current source, delta, linked opening document/payment, version and audit. Status is `current`, `reconciliation_required`, or `source_unavailable`; legacy operations remain unchanged. Source changes never silently update posted financial documents.
* `POST /links/:id/acknowledge` takes `{version,source_hash:current_source_hash,reason,related_document_ids:[],related_payment_ids:[],idempotency_key}`. New evidence must be posted, non-opening, belong to the same customer, postdate the last reconciliation and never have been used on another link. Document net effect must equal the change in old receivables minus the change in old settlement reductions; cash effect must independently equal the change in approved old receipts. Matching only a zero overall balance is insufficient. New credits against prior evidence must be included explicitly. If a prior payment proof is reversed, replacement evidence must restore the lost effect; old proofs and every acknowledgment remain in the audit trail.
* `reconciliation_count(session, as_of=None)` is the accounting closing hook. It counts changed, unresolved or unavailable sources and invalidated evidence for linked orders whose cutover is on/before the cutoff, using the caller's settings lock and transaction.
* Link responses also include `required_document_amount`, `required_payment_amount`, and `required_documents:[{id,number,amount}]`; these reflect invalidated prior evidence as well as old-source changes. A matching replacement payment can repair a reversed proof even when the old source hash is unchanged. The original proof and its previous effect remain in audit history.
* `POST /links/:id/revoke` accepts `{version,reason,idempotency_key}`. It is allowed only before opening confirmation, in the open cutover period, without subsequent reconciliation evidence, active allocations, external posted credits, or refunded use of the opening advance. It reverses the generated opening entries in the same transaction and changes `link_status`/`status` to `revoked`; all documents, reversals and audit remain. `can_revoke` and `revoke_blockers` expose the precise conditions. A revoked order can be reviewed and imported again during the same valid cutover window, reusing its unique link with a newer version and a new opening document/payment. Active imported opening documents cannot be directly reversed through normal document/payment actions. Damaged historical targets are exposed as unavailable and cannot be disguised using normal cash receipts.
* Normal-direction payments and credit documents return `available_amount`, capped by the partner's unallocated balance after refund reservations. Their original `unallocated_amount`/`residual_amount` is still retained. Partner lookup accepts `include_inactive=1` for read-only statement selection; normal new-document selectors default to active suppliers.
